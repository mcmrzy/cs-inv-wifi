# BMS 诊断固件 0.4.3-bms-diag4

用于当前 ESP32-C3 Modbus 面板，保留黑蓝 LVGL 界面和 0.4.2 屏幕启动修复。独立 UART1 使用原 direct 的 BBJ 协议：GPIO21 TX、GPIO20 RX、9600 8N1、无软件反相，DE=-1 配合现有硬件自动换向。查询为 `7C 78 24 80 01 00 00`。不扫描其他波特率，不发送电池设置、校准或升级命令；原有人工发起的升级功能仍受原流程控制。

## 更新与抓日志

已有完整面板分区的设备使用本版 App bin 更新。串口单独烧录 App 地址为 `0x20000`，不需要擦除 NVS、SN、配网和工厂数据。版本应显示为 `0.4.3-bms-diag4`。USB Serial/JTAG 终端可按115200打开；BMS线路仍为9600。

从上电开始抓取30～60秒完整日志；若中途接入，也会在10秒内输出任务状态。保留 `BMS_DIAG_BOOT`、`BMS_DIAG_STATE`、同一 `seq` 的 `BMS_DIAG_QUERY`、`BMS_DIAG_RESULT` 和全部 `BMS_DIAG_HEX`。同时记录电池接入时间。不要只截取 `INV_LINK`，那是另一条 UART0 逆变器链路。

## 输出含义

- `BOOT`：固件版本、实际编译引脚、协议、方向和超时配置。
- `STATE`：每10秒输出一次，含 `RUNNING / NOT_STARTED / PAUSED / IAP / STALLED`，查询次数、完整有效帧次数、总接收字节、最近结果、帧错误、校验位错误、溢出、发送失败和采集任务栈余量。`trace_dropped`是日志快照因消费不及时而丢弃的次数，不等于UART丢字节；`logger=main_loop`表示日志由主循环输出。
- `QUERY`：每次查询后输出，含 `tx=7/7`、`tx_done=0`、收帧前被清掉的迟到字节数、RX数字状态、收字节数、分批次数、首次读到数据的耗时和总耗时。`first_read_ms=4294967295` 表示本次没有读到数据。
- `HEX TX/RX`：每行16字节，`offset` 为该次报文的字节偏移；最多256字节接收缓存，不截成只有头部。`OLD_RX` 是下一次查询前的迟到/残留数据，超过256字节的剩余部分由原清缓冲操作丢弃；`discarded` 给出清理前的缓存量。
- `RESULT`：BBJ头、地址、功能码、声明长度、CRC、单体/温度数量和完整pack信息校验结果。`parser_ok` 是原direct实时值解析器结果，`summary_ok` 是原完整汇总解析器结果；用于区分宽松实时解析和完整报文校验。
- `SAMPLE`：原解析器接受的电压、电流、SOC/SOH原始值及百分比除数；单位直接标在字段名中，未改换算。
- `ACCEPT`：本次已提取并接受一帧完整BBJ应答；offset/length对应原始RX中的位置，`crc_checked=1`表示已通过完整校验。diag4会用此帧更新实际BMS快照，屏幕和上报也使用这份真实数据。

| reason | 含义与下一步 |
| --- | --- |
| `NO_RX` | 本次没有收到任何字节。检查BMS供电、A/B、共地、发送波形和接收电平。不能只凭此码认定是哪一端故障。 |
| `ECHO_ONLY` | 只收到与查询完全相同的7字节，不能视为BMS应答。 |
| `SHORT_HEADER` / `LENGTH_MISMATCH` | 短帧或收帧长度与头部不符，结合HEX、首次接收耗时、UART错误和波形定位。 |
| `BAD_CRC` | 实收整段的CRC不符，可能有位错误、丢字节或多段数据拼接。 |
| `BAD_HEADER / BAD_ADDRESS / BAD_FUNCTION` | 收到了不符合本次BBJ查询的头部或其他数据。 |
| `BAD_CELLS / BAD_TEMPS / SHORT_PACK / BAD_VALUES` | 数据结构或换算范围不匹配，需要核对实际BMS协议版本。 |
| `FRAME_IN_BUFFER` | 噪声、查询回显或尾部数据中存在完整有效帧。按candidate_offset/candidate_length定位；diag4提取严格校验通过的应答并发布实际电池数据。原始HEX完整保留。 |
| `VALID` | 该次完整缓冲是一帧通过完整BBJ校验的应答。 |

正常查询间隔500ms，连续10次失败后仍按原策略每5秒重试；每次查询生成一份固定大小快照，主循环输出结果，不再等5分钟才看得到失败原因。主循环每次最多消费两份，静态队列共四份，满时计数丢弃日志快照，采集继续。启动期主循环尚未就绪时，日志可能延后出现，使用`captured_ms`确定实际收帧时间。详细日志不在UART采集任务中格式化。诊断版为等待UART硬件发送完成额外调用一次最长50ms的TX等待。

diag4保留完整300ms诊断监听（或直到256字节缓存满、驱动读取报错），不因回显后静默30ms提前结束。普通0.4.3同样不会因查询回显提前结束，收到完整、严格校验通过的应答即返回。对每批UART字节累积搜索，兼容查询回显后跟快速或延迟应答、碎片回复、前导杂字节及错误帧后跟有效帧。

发送前清理上一事务残留，发送后不再清接收缓存，避免误删快速回复。软件始终使用普通UART、9600 8N1、无反相，未尝试用反相或内部上拉补偿RX分压或总线偏置。

实机diag3日志目前只有7字节查询回显，完整约318ms窗口内尚无电池应答；用户确认同一电池接口在BBJ上位机正常。diag4修复的是回显/杂字节与有效应答拼在一起时的软件拒收问题。若diag4仍只收到7字节且无ACCEPT，需要继续测控制板RS485发送波形、BMS端收到的请求及RO/GPIO20电平，不能声称软件已让实机读通。

## diag2重启修正

实机日志为`Stack protection fault`，对应ELF SHA256为`0c412fab0d48f15271d66831864d800f602d64f110c1d9f1c3d8d4d995fac06a`。精确解码显示异常现场在中断入口，报出的`0x3fc9d3d0–0x3fc9d9d0`与1536字节的`xIsrStack`相符；仅凭任务名和该现场不能确定最初越界的是哪个调用。

diag3移出UART采集任务内的新增长日志和HEX格式化；固定大小快照由主循环消费。诊断采集栈为6144字节，中断栈为4096字节，保留硬件栈保护与FreeRTOS栈金丝雀。目标编译器生成的采集函数自身静态栈帧为672字节，不能将它等同于完整调用链峰值；实际余量由运行日志的`stack_free`观察。目标机器码也核对了采集函数不直接调用日志格式化。实板持续运行仍需更新后验证。

`tx=7/7` / `tx_done=0` 只说明ESP驱动接收请求并完成UART发送，不证明485线上已正确送达BMS。`rx_idle`是瞬时数字采样，不能测量GPIO电压。日志不能替代对RX分压及A−B差分电压的示波器测量，也不能用软件修正不兼容电平。

## 复现构建

运行 `build.ps1 -BmsDiagnostic`，使用独立 `build_bms_diag`、`sdkconfig.bms_diag` 和编译开关 `PANEL_BMS_DIAGNOSTIC=ON`。普通 `build.ps1` 显式关闭开关，保持独立的 `build_full` 产物。当前目标是提供定位证据，实板读取结果待抓日志确认。

# L10 串口管理员修改 SN（已确认，ARM App CS 0x09）

## 目标与现状

在 `esp32c3_l10_idf` 增加单行命令 `set_sn <管理员密码> <新SN>`。
入口使用现有 USB Serial/JTAG 虚拟串口；UART0 保持为 ARM 通信通道。
当前 ARM 通信使用 CS 帧（双层 TEA、CRC32、PPP），SN 从 0x06 只读信息的偏移 10..25 读取，为 16 字节 ASCII。
当前 ESP 会自动采用 ARM 的 SN 并重启，因此不能只修改 ESP NVS。

## 推荐流程

1. 接收有长度上限的单行输入，支持 CR/LF；溢出整行丢弃，密码及整条输入不进入日志、不回显。
2. 验证独立的管理员密码与 SN；密码通过构建配置设置，空密码禁用修改功能，不复用 MQTT 密码。
3. 在主循环中提交操作，避免控制台任务直接与 ARM 轮询状态竞争；OTA 或另一条 SN 操作进行中返回 BUSY。
4. 通过现有 CS 编码器发送用户指定的 0x09 写 SN 命令；Param1=0，Param2=16，SN 按 ASCII 自然序右补零。
5. 获得成功应答后，立即请求 0x06 回读并比对目标 SN；操作期间避免旧信息触发现有 SN 同步重启。
6. 回读一致才提交 ESP NVS，清理旧 MQTT retained 状态并重启；运行中的 g_device_sn 保持原值，暂停身份相关工作，重启后加载新 SN，使 MQTT client ID、主题及 BLE 名称一致。
7. 认证失败、ARM 错误应答、应答超时或回读不一致返回具体失败结果，ESP 保持原 SN。若 ARM 已修改而 NVS 保存失败，需要明确报告两端未同步，并通过回读恢复，不宣称原子事务成功。

## 已确认决策

- 用户指定独立管理员密码，并接受命令与流程，授权依照现有命令设计帧格式。
- 用户随后将写 SN 命令从 0x10 改为 0x09；本次按最新要求实现。
- ARM App 请求：CmdLen=24，CMD=0x09，Param1=0，Param2=16，Data 为 16 字节 SN。
- ARM 应答：CmdLen=12，CMD=0x09，Param1=0，Param2=1，Data[0]=0 成功，非零失败；ARM 持久化并更新只读信息后应答，不重启 ARM。
- SN 输入为 1..16 位 ASCII 字母数字，短 SN 右侧补零；写成功立即 0x06 回读，两个应答窗口各 800ms。

仓库未包含 ARM 的 Collector.c/Collector.h；现有模拟器也没有 0x09 写 SN 分支。
旧 `0xAA` 协议文档将 0x10 定义为 OTA_START，当前 ARM OTA 实现实际走 CS 0x07/0x09..0x0B。本次 App 0x09/Param1=0 写 SN 与 Boot 0x09/Param1=1..3 查询固件信息按模式分发，且操作与 OTA 双向互斥。

## 验证目标

- 正确密码和合法 SN：仅发送一次正确编码的 0x09，成功回读后持久化并重启。
- 密码错误、空密码、非法/超长输入：不发送、不保存、不泄露密码。
- ARM 拒绝/超时/回读不一致：返回失败，不提前更新 ESP 身份。
- OTA 忙、重复命令、旧 0x06 应答：不发生串口争用、误提交或错误重启。
- NVS 失败：报告保存失败，不进入反复重启。
- 运行 host 回归和 ESP32-C3 固件构建；实物串口、ARM 持久化和重启后的两端一致性单独验收。

# 0.6.43：LCD 1MHz 单变量对照

## 0.6.42 实机结果

用户确认两段日志中的实物现象仍是“有按键蜂鸣，但画面始终不变”。日志版本为 `0.6.42-lcd-phase-diag`。

已确认的软件路径：

- 两次均出现 `LCD_SPI_PRIMED`，Logo 淡出、首次绘制返回 `ok=1`。
- 第一段：`KEY_EVENT queued=1` → `LCD_KEY received seq=1` → `applied page=1` → `LCD_RENDER page=1 tx=2191 errors=0`。随后页面切换、选中项变化和发送计数继续推进。
- 第二段：12 个按键事件被消费，页面在 0（主界面）与 1（菜单）之间切换；选中项变化，发送次数从 1513 增至 2023，驱动错误仍为 0。
- 对应画面仍不变，故不能将故障归为“按键未入队”或“界面任务未响应”。尚未取得屏幕端波形/返回值，驱动发送成功不能确认屏幕收到有效命令和像素。
- 个别按键没有改变页面/选中项，绘制函数返回但 tx 不增加，属于相同像素条带跳过；不能单独认定为卡死。
- 第一段 BLE 因内部空闲 RAM 63584 小于准入门槛 65536 被暂缓，随后重试并在约 17 秒广播；第二段约 7 秒广播。这个暂缓是明确日志，不是未启动蓝牙的猜测。手机扫描与连接结果未提供。

此前的首次 SPI/复位顺序修正仍保留，但本次实机证明它尚未消除“画面不变”，不能把该候选问题报告为最终根因。

## 本版只验证一个假设

假设：降低 LCD 时钟可增加发送建立/保持时间余量，从而帮助区分频率相关的通信问题。该假设尚未得到硬件验证；1MHz 不是确认修复。

本版从**确切 0.6.42 独立源码快照**复制，所有 `.c/.h`、寄存器初始化、复位等待、SPI mode3、DMA、CS/引脚、蓝牙、MQTT 和诊断逻辑完全不变。仅修改：

1. 构建配置 `CONFIG_DIRECT_LCD_SPI_CLOCK_HZ` 从 8000000 改为 1000000。
2. 嵌入版本改为 `0.6.43-lcd-slow-diag`，用于区分实机日志。

逐文件比对确认除了 `sdkconfig` 与 `version.txt`，源快照无差异。主工作区配置、版本号和原发布镜像均保留。

ST7789P3 的串行写入对 SCL 脉宽、SDA 与 D/C 建立/保持时间及边沿有要求；不能仅凭名义频率判断实物波形合规。手册第 38 页为四线串口时序，第 98 页说明 CS 可以永久接地。本轮不根据症状要求改变 CS 接线，也不占用 GPIO4。[Sitronix ST7789P3 手册](https://files.waveshare.com/wiki/ESP32-S3-GEEK/ST7789P3.pdf)

历史文档有更早的低速/软件 SPI 失败记录，但那些版本和接法/初始化背景不同，不构成本次同代码、仅改频率的对照结果。

## 操作与结果判断

这是临时对照版，不是正式修复版。1MHz 会明显延长 Logo 动画和整屏绘制，启动可能需要十余秒；按键后等待约 2 秒再判断，避免把低速刷新当作新的卡住。建议通过现有 USB App 维护流程写入并保留 NVS/factory；这是 App 镜像，不能写到地址 0，不使用整片擦除作为本实验步骤。没有关闭或放宽 OTA 健康检查；若用 OTA 且启动检查失败，不应反复强行确认镜像。

分别记录几次完全断电上电与仅复位，观察 Logo、白屏和菜单切换。故障出现后先不要重启，短按 ENTER 打开菜单、等待 2 秒，短按 ESC 返回、等待 2 秒，并保留完整日志。不要进入确认参数写入的操作。

- 1MHz 正常、8MHz 失败：支持频率/时序余量相关的假设；仍需进一步定位边沿、接线、电源或驱动时序，不能据此唯一归因某个器件。
- 两版均失败且 `page/keys/frames/tx` 均推进：停止继续叠加软件参数，采集 LCD 连接器端 SCL、SDA、D/C、RESET，以及电源波形，核对实际送达屏幕的信号。
- 若菜单页面能变化但刷新慢：记录绘制耗时与外观，区分故障消失和低速实验固有延迟。

采集点沿用已确认的 ESP GPIO6/SCL、GPIO7/SDA、GPIO9/D-C、GPIO10/RESET，在屏幕连接器端取信号。当前为 mode3、8 位、MSB-first、CS 固定低，无需 CS 边沿分帧；逻辑分析仪最好至少 10MHz 采样检查 1MHz 字节序列，模拟电源/边沿仍需示波器。应核对 D/C=0 时的 `01`、`28`、`11`、`36/70`、`3A/55`、`2A/2B/2C` 与后续像素；电源/RESET 电平须当前实测，历史静态读数不能代表本次启动。

本轮未连接或刷写设备，不宣称白屏/冻结已修复。无新增功能代码，前轮生产全套回归中的既有 `direct_battery_validate` 链接依赖问题仍未解决。

## 实机反馈更新：43 确实会更新画面，但很慢

用户后续提供两段明确为 `0.6.43-lcd-slow-diag` 的日志：Logo 耗时 8696/8162ms，首次绘制 1355/1361ms，整页切换 1322–1868ms，SPI 错误均为 0。用户随后修正现象为“按了按键确实会有变化，不过很慢很卡”。因此不能继续以“软件已变化、屏幕完全不响应”为既定事实，也不能据此判断物理链路已失效。

本版阻塞式绘制期间不消费新的界面按键；按键扫描任务独立入队并蜂鸣。绘制返回后，显示任务一次取完积累的队列，再绘制最终状态。例如第二段日志 13.323 秒进入报警页，15.193 秒绘制完成；期间排队的按键随后把状态从报警页切到菜单，再返回报警页，最终像素相同而 tx 保持 1135。这是低速绘制与队列批处理造成的中间页面不可见，不是该处死锁的证据。

此前曾建议结束 1MHz 的性能对照，回到 8MHz 的 0.6.42 比较响应速度；该建议已被后续现场反馈修正：42 也会偶发停留在清晰 Logo，不能作为可用或稳定基线。此前 42 日志中的对应绘制约 0.25–0.35 秒，只能说明那些启动的软件绘制耗时。低速与队列分析只解释 43 的慢和部分中间页面不显现，不能解释或排除 42 的 Logo 停留以及曾报告的纯白屏。没有据此另行生成叠加参数的新固件，也没有执行刷机。

## 最新反馈：42 偶发停留在清晰 Logo

用户明确确认 Logo 一直清晰不动，而非已经淡出后未出现主界面。本次失败启动的对应日志尚未取得，不能将此前成功执行淡出和首次绘制的日志套用于本次。

源码核对：`direct_splash_run()` 完成 8 级淡入后仅固定等待 500ms，随后执行 3 级淡出；不等待 Wi-Fi、BLE 或 DSP。淡出与主界面使用同一显示任务、同一条 SPI 发送路径和同一个静态条带缓冲。返回后显式清除 `s_have_previous` 并设置 dirty，强制首次全屏绘制。因此未发现“等待联网才跳转”或“首次刷新被条带缓存跳过”的代码依据。仍需区分任务停在等待/发送、被其他任务阻塞，以及发送返回但显示端未更新。

下一步保留当前 42 镜像，在一次故障持续期间采集从启动到卡住后至少 40 秒的连续串口输出，并以 ENTER、等待 3 秒、ESC、等待 3 秒作为事件标记。重点对应 `LCD_BOOT_SPLASH hold/fade_out/frames`、`LCD_UI_FIRST_FRAME` 和后续 `LCD_DIAG`；单条 `stage=SPLASH` 在正常动画中也会出现，须比较多条诊断的 stage_age、spi_age、tx 是否继续推进，不能仅凭一次采样认定死锁。`ok=1/errors=0` 只代表软件发送返回，不代表屏幕实际接收成功。

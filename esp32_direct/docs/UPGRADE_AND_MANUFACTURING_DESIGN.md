# 升级、身份写入与量产测试方案

更新：2026-10-13。适用：ESP32-C3 独立控制器，ARM 未焊，DSP/BMS 直连。当前 v0.6.1-production-dev，使用说明见 [工厂工具](../tools/README.md)，实施记录见 [执行记录](superpowers/plans/2026-10-12-production-execution.md)，下游新增证据见 [协议核对](TARGET_PROTOCOL_EVIDENCE.md)。尚未完成实机升级、校准与带载验收。

## 2. 升级界面与执行边界（目标要求，完成状态以上表为准）

系统菜单增加「设备信息」「固件升级」，量产维护独立进入。

- 固件升级入口列出控制器、DSP、BMS，显示在线状态、当前读回版本、可升级能力；未实现的目标明确显示“暂不支持”。
- 网络和手机蓝牙只是固件来源；屏幕不接收大文件，也不维护第二套升级状态机。通过 `ota_service_get_snapshot()` 获取状态，沿用现有颜色/字体/中英主题和条带渲染。
- 接收/下载→校验→写入→重启→启动确认。页内显示目标、目标版本、来源、百分比、已收/总字节、当前阶段、失败原因。下载 100% 不显示“升级成功”。
- 同时只允许一个目标；收取数据期间按键不能写功率参数、恢复出厂或重启。取消按钮由当前状态可取消性决定，不能直接断开正在擦写的下游目标。
- 启动新固件后显示确认结果；下游升级必须拿到最终 ACK/CRC 并重新读取目标身份与版本才成功。未获得版本读回能力时只能报告“传输完成，等待验证”。
- DSP/BMS 刷写前使用型号、硬件版本、Boot 协议、固件类型和容量匹配。逆变器进入已确认的维护停机状态；停机/零功率确认及独立保护保留，不能用停止轮询代替停机。
- UART0/1 各有一个事务所有者，正常轮询、参数写入和 Boot 升级排队互斥。BLE/MQTT 工作者不得绕过所有者直接抢 UART。
- 固件策略把开发允许 HTTP/无签名与量产策略分开；现版哈希、签名可选，不能称为强制签名量产方案。量产签名发布仍需与服务端的实际发行机制协调。

原协议资料已经在本地，继续实现时直接读取：

1. `Boot(9)/Boot/source/ComDSP/UsartDsp.c`：DSP Boot 线协议与最终 ACK，区别 ESP↔ARM 外层封装。
2. `Boot(9)/Boot/source/Collector/BmsUpdate.c` 和 `bmsBoot(7)/Boot/app/update_protocol.C`：BMS 的 `0xFF/FE/F9/FD/FC`、块大小、错误码、CRC32、复位与版本确认。
3. 编解码测试只证明字节构造正确；接收超时、自动换向、擦除与掉电恢复必须单独实机验证。旧源码变量名或旧 OTA 目标枚举不能证明兼容。

## 3. 出厂数据写入机制（待实现）

### 两种构建配置

- `device`：保留当前指定 SN 的单机镜像，明确标记不可批量复用。
- `production`：固件不含固定 SN；启动读取 factory 身份，未写入/校验失败时进入待生产状态，不联网冒充一台正式设备，不生成替代正式 SN。

### 数据分工

| 数据 | 真实来源/写入者 | 保存位置与规则 |
|---|---|---|
| 整机 SN、产品型号、整机硬件版本、板卡版本、批次、生产时间 | 产线扫码/工单与治具校验后写入 | 独立 factory NVS 分区；SN 与芯片 MAC 绑定；锁定后仅授权维修流程修改 |
| ESP 固件版本、构建号、镜像 SHA256 | 已运行固件的编译元数据与发行清单 | 只读；OTA 后自然变化；产线记录实际读回值 |
| DSP/BMS 硬件、应用、Boot 版本 | 目标通信读回 | 可缓存，但需注明在线/失效；无协议读回则标“未知”，不填写入时声称值 |
| 校准系数、算法版本、温度与仪器信息 | 明确通道归属后，由校准程序/目标 MCU 写入 | 真实采样 MCU 保存实际生效系数；ESP factory 存引用/副本和验证摘要；禁止只改 ESP 显示值掩盖误差 |
| 设备凭据 | 已接入的后台发行机制 | 不导出到明文测试报告；当前 MQTT 密码编译固定，不能仅写 `dev_key` 就宣称逐台鉴权 |
| Wi-Fi、主题、语言、时区、用户配置 | 用户 | 普通 NVS；恢复用户设置不擦 SN、出厂校准与生产记录 |
| OTA 待确认记录、安全版本 | 升级服务 | 保持独立；出厂/维修流程不能无意重置防回退状态 |

### 工具与事务

治具使用现有 USB Serial/JTAG 接口，避免再占 DSP/BMS UART 和 GPIO。先实现带版本的工厂帧：长度、请求 ID、命令、payload、CRC；响应匹配请求 ID，所有写操作有限时、校验及明确错误码。不能从普通诊断日志中推断写入成功。

建议流程：`读取芯片/板卡信息 → 获取工单SN → 校验格式/重复/绑定 → 写暂存完整记录 → 读回逐字段与CRC → 提交有效记录 → 断电重启再读 → 测试 → 放行锁定 → 导出报告`。

记录含 schema、generation、SN、型号、各板硬件版本、生产批次/时间、校准版本/摘要、锁定标记与 CRC。采用两个 blob 槽：写非当前槽并 commit，完整读回验证后选取最新有效 generation；断电后只选择有效完整记录，防止部分字段拼成新身份。CRC 用于一致性校验，授权由单独的工厂/维修访问机制承担。

工具 `inspect / provision / verify / test / export`；重试相同请求必须幂等。同一 SN 被不同 MAC 使用时停止并交由生产系统处理；本地离线多工位需要共享或预分配 SN 范围，单台工具无法保证跨工位全局唯一。

### 分区和重置

当前没有 factory 分区；现有 nvs 是 `0x9000/0x6000`，cache 是 `0x360000/0xA0000`。拟从 cache 尾部划出专用 factory 分区，保持两个应用分区边界；具体容量由数据量及 NVS 容量验证决定，**此版没有修改分区表**。

分区改变要做有线迁移/首烧，应用 OTA 不替换分区表。原 cache 需先导出必要数据并在新边界重建，禁止把新 factory 区当成旧 SPIFFS 尾部继续写入。

现有 `storage_init()` 在 NVS 异常时会 erase 默认 NVS；`storage_factory_reset()` 擦 `inv_cfg`，包括现有 SN/key。因此正式身份不能继续依赖这一区域。独立 factory 异常必须进待维修态，不能自动擦除或自动再造 SN。

完整 4MB 镜像在地址 0 写入会覆盖出厂数据。量产采用公共程序分段写入＋逐台 factory 数据，不分发带整台数据的通用全量镜像；维修工具默认保留 factory 并先读回备份，授权清除要单独记录。

## 4. 校准与验证测试（待实现）

产线按四个阶段运行，每项分别有 PASS/FAIL/SKIP、阈值版本、原始数据与耗时；未测不算通过。

| 阶段 | 自动/操作员项目 | 通过依据 |
|---|---|---|
| 控制板低压测试 | 供电、4MB Flash/分区、复位原因、堆余量、身份CRC、显示纯色/图案、六键、蜂鸣器、USB | 实测/读回；显示与声音需操作员或治具确认，GPIO回读不能证明屏幕显示/蜂鸣器发声 |
| 通信和联网 | DSP/BMS 身份与有效CRC帧、断线重连、读取配置、BLE扫描/连接、测试Wi-Fi、云端测试账号 | 实际收发记录、正确字段单位、规定窗口内恢复；不把无线扫描等同连接成功 |
| 采样校准 | 电池/PV/交流电压电流、温度；零点及多点；通道与量程由真实采样源确定 | 可溯源仪器参考值→系数计算→目标写入→读回→独立验点→掉电再验；阈值取硬件规格，不能凭空设定 |
| 整机放行 | 指定负载/充电/旁路/告警保护、ESP网络与BLE升级、DSP/BMS升级、老化、配置/身份保持 | 独立电气治具与既定工艺控制负载；刷写后版本读回、关键点断电恢复；测试完回到出厂默认用户配置 |

原 ARM 的 `USERFLASH.h` 存在 `VpvGain/VpvOffset/VoutGain/VoutOffset`；`UsartDsp.c` 的“DSP校准参数”注释分支被注释。仅凭这些字段不能得出 DSP/BMS 可写校准命令已经完整实现，需继续追踪系数实际应用位置与目标协议。

报告绑定 SN、MAC、型号、各硬件/固件版本、镜像 hash、治具/仪器编号、仪器校准日期、操作员、工单、原始测量、阈值、校准前后值、故障和重试记录、最终放行状态。测试记录大文件保存在工位/生产系统，设备仅保存摘要，避免耗尽4MB空间及反复写 Flash。

## 5. 风险与实施顺序

| 优先级 | 证据与影响 | 修复/验收 |
|---|---|---|
| 阻断批量发布 | `ensure_sn()` 每次强制同一 SN | 独立 production 配置、factory档案、两台不同SN重启与联网验证 |
| 阻断 DSP/BMS 升级发布 | manifest 明确拒绝非 ESP；旧传输依赖未焊 ARM | 实现直连事务和目标兼容检查；按最终ACK/CRC/重启版本验证，不提前解禁 |
| 阻断正式校准放行 | 缺完整仪器/通道/系数协议与阈值 | 先确定通道字典与校准归属，再实现写入、读回、独立验点 |
| 重要 | 现有身份与默认NVS同区且有擦除路径 | factory独立保存，异常不自动清除，迁移/维护镜像规则 |
| 重要 | ESP升级允许无hash/签名/HTTP；BLE本地无绑定鉴权；OTA没有硬件型号匹配 | 开发/生产策略区分，按产品访问策略完善，签名发行与后台协同；错误型号镜像拒绝测试 |
| 重要 | 主循环存活即可确认ESP镜像 | 增加关键服务就绪/分区/NVS判定；外设可选能力与真实硬件故障分开，避免误回滚 |
| 建议 | 无统一屏幕升级状态与产线反馈 | 状态快照页、目标能力列表、可操作取消/失败恢复；条带渲染避免大framebuffer |

实施顺序：① ESP/BLE 升级状态界面与回归；② 生产档案＋USB工厂协议＋写入/验证工具；③ DSP/BMS直连Boot；④ 仪器校准与整机工艺放行。每阶段单独产物与实机验收，生产分区迁移单独发布。

仍需用户/硬件工艺提供的输入：正式型号及整机/控制板/DSP/BMS硬件版本命名，工单SN规则与生产系统接口，采样通道精度与仪器/负载条件，以及当前DSP/BMS的实际Boot/应用版本。已有本地ARM/BMS源码无需重新提供。

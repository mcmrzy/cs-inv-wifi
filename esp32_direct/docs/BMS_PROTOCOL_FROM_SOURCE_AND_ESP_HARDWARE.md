## 2. BMS 接收流程

`bsp/libraries/drivers/drv_uart.C` 和 `kernel/components/drivers/include/drivers/serial.h`：USART1，PA9 TX/PA10 RX，默认 9600、8 数据位、无校验、1 停止位。

`app/uart_communicate.c:70-140`：每个接收字节重置 5 ms 定时器；定时到期后取出接收队列，整批分发给已注册协议处理器。不是按头扫描并重组的字节流解析器。

`app/PC_485_protocol.C:91-117` 的校验要求：

1. 接收批次至少 7 字节。
2. 实际批次长度恰好等于 `7 + data_len`。
3. 第一个字节为 0x7C。
4. CRC16 正确。

它没有扫描前导噪声，也没有将一个批次里的多帧拆开。收到不完整帧、噪声前缀或粘包时拒绝该批次。**这些拒绝分支本身没有蜂鸣调用**，所以不能用“可能丢帧”直接解释四声。

本工程 PC 校验函数没有拒绝其他地址；回复地址固定为 0x80。当前使用 0x80 与 ARM 请求一致。

## 3. 帧格式和实际查询

全部多字节整数为小端，头部紧凑打包为 7 字节。

| 字节偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | Head=0x7C |
| 1 | 2 | CRC16，低字节在前 |
| 3 | 1 | Address |
| 4 | 1 | Function code |
| 5 | 2 | Data length，仅计算数据域长度 |
| 7 | N | Data |

CRC 算法为 CRC16/Modbus，初值 0xFFFF，反射多项式 0xA001。覆盖范围是从字节 3 的 Address 到数据域末尾，不包含头部和 CRC 字段。

只读电池查询：

```text
7C 78 24 80 01 00 00
   ----- -----------
   CRC   参与 CRC 的四个字节
```

CRC 计算值为 0x2478。9600 8N1 下 7 字节发送时间约 7.29 ms。字节间若有超过约 5 ms 的空闲，BMS 接收任务可能把请求提前拆开；同一批次不能混入 ROM 日志或第二条请求。

用户提供 V1.6 文档建议 500 ms 轮询；BMS 此接收代码没有对 0x01 加 500 ms 频率检查。ARM 的 100 ms 任务交替 TX/RX，正常发送约每 200 ms；ESP 对照版为 500 ms。现有实测说明修改该周期未消除鸣叫。

## 4. 0x01 回复：本工程固定 110 字节

源码 `PC_485_protocol.C:44-88` 固定 16 节电芯；`CELL_TEMP_NUM=2`，再加 MOS/PCB 温度，共 4 个温度。`drv_pc_protocol.h` 的 `pack_info` 为 61 字节。

数据域长度 = 1 + 16×2 + 1 + 4×2 + 61 = **103 字节**。

完整回复长度 = 7 + 103 = **110 字节**，头部为：

```text
7C CRC_L CRC_H 80 01 67 00 10 ...
```

9600 8N1 下，仅完整回复在线上传输就约 114.58 ms，还需计入 BMS 的接收判帧和任务调度时间。

### 0x08 与旧协议/当前 ESP 不一致

`PC_485_protocol.C:421-433,618-664` 的版本请求包含两字节，fw_type=0 为 App，非0为 Boot。回复数据域为 `type + fw_type + byte[24]`，26 字节，完整33字节。

例如查询 App 软件版本：`7C FF A2 80 08 02 00 00 00`。

ESP 当前 `direct_bms_identity.c` 仍发一字节 type，期待32字节回复，因而不兼容这份 BMS 程序。它只在 USB 显式请求时调用，不是日常轮询自动发送项；不能将它认定为当前鸣叫原因。

## 6. 对当前 ESP 实现的核对

- GPIO21/20、9600 8N1、0x01 请求和 CRC 均匹配 BMS。
- 接收缓冲256字节、300 ms等待窗口，能够容纳本工程的110字节回复；实际收发器若有自身回显，当前整个批次CRC解析不会自动跳过回显，需要波形确认有无回显。
- `direct_bms_parse_7c()` 没有按头部 data_len 严格确认完整数据域，也未校验回复地址和功能码；不能把任意 CRC 正确的7C数据都当电池回复。
- SOC/SOH 当前直接保存原始0–1000数值到名称为百分数的字段。源码模拟中62.5%被保存成625；这属于显示/转发单位问题，不能解释只连接BMS且无DSP时的BMS蜂鸣。
- 当前常规路径没有发送BMS蜂鸣、治具控制、自锁解除或MOS控制命令。

## 7. 与四声相关的结论边界

这份 BMS 代码的正常查询和校验失败路径均没有“四声”调用。治具蜂鸣要求另一协议头0x2B和有效CRC；其初始化导出被注释。长按唤醒键可生成相同四声节奏，但截图未建立它与ESP的连接，不能据此归因。

UART数据在 `low_power_task.c:74-77` 另一个注册回调中会清除强制关机标志。这是接收任意UART数据的行为，ARM与ESP都有同样影响；该回调也无蜂鸣。

已完成宿主对照：使用ESP实际组帧函数，执行BMS原始CRC过滤、查询回复和pack_pack_info代码（公共数据及设备写入用模拟值），验证请求被接受、返回110字节及上述拒绝行为；结果见 `tmp/bms_protocol_diagnosis/endpoint_test.log`。此证明协议软件兼容性，不证明实机线上信号或实机BMS固件版本一致。

### 8.1 GPIO4 固定低与 CAN 收发器的冲突

用户最新确认：U30、R228 仍焊着，CANH/CANL 也连接到 BMS。因此下述共线和总线连接条件已成立；未取得拔线对照或示波器实测，四声因果仍待验证。

修复前0.6.3的 `sdkconfig:520-521` 为 LCD CS=4、CS_FIXED_LOW=y；`main/direct/direct_panel.c:88-92` 在启动准备时将 GPIO4 配成输出低。应用源码未发现 TWAI/CAN 初始化或发送调用。芯片能力配置 SOC_TWAI_SUPPORTED=y 不代表应用使用 CAN。用户随后确认屏幕NSS已经独立硬件下拉，从0.6.4改为LCD CS=-1、GPIO4固定高，见第9节。

原 ARM 图纸为 GD32F303Cx，CAN TX=PB9，屏幕 NSS=PB12，是不同引脚。ESP 将 GPIO4（原网络 ARM-BMS-CANTX）复用为屏幕 NSS，同时仍保留接 U30 的 R228，形成了 ARM 没有的硬件共线。即使两者的 RS485 请求字节相同，也不能认为所有连接状态相同。

但网络 ARM-BMS-CANTX 同时经过 R228=100Ω 接 U30（SN65HVD230）的 D 输入，U30 的 RS 接地，属于驱动使能的高速模式。因此若 U30 和 R228 仍装着，屏幕 NSS 的固定低也会让 CAN 物理输出持续显性：CANH 高、CANL 低。这不需要 CAN 软件启动。

- 若 CANH/CANL 也接着 BMS，这是一条具体的总线干扰路径，优先只断开两根 CAN 线进行对照，保留 RS485 和供电。
- 若 CANH/CANL 未接 BMS，此路径不能直接向 BMS 输入 CAN 显性电平；仍不能仅凭原理图排除共用电源上的间接影响。
- 若 U30 未装或 R228 已断开，则上述 D 输入共线条件不成立；R228 断开后，芯片侧 D 应保持明确的高电平，不能把屏幕侧 GPIO4 改高，否则 NSS 失效。

此结论来自器件真值表和实际 GPIO 配置，不代表已经证实四声由 CAN 引起。[TI SN65HVD230 数据手册，功能表 2、3](https://www.ti.com/lit/gpn/SN65HVD230)。

补充 BMS 源码核对：`app/can_communicate.c:99` 的任务初始化导出被注释，多个 CAN 应用协议初始化也被注释；`bsp/libraries/drivers/drv_can.c:1023` 仍有板级 CAN 驱动注册。不能把 CAN 持续显性直接等同于触发某个已运行的 CAN 蜂鸣告警：目前没有找到这种四声调用链。优先断开 CANH/CANL 对照是为了检验硬件冲突与鸣叫是否有因果关系。

### 8.2 RS485 接收电平缺少转换

U31 VCC=5V；其 RO（1脚）经过 R231=100Ω 直接接 ARM-BMS-485RX，即 ESP GPIO20。R229=1kΩ 把 MCU 侧 RX 上拉至 3.3V。

RO 是具有三态功能的逻辑输出，不是仅靠外部上拉产生高电平的开漏输出。R229 只在接收输出禁用/高阻时提供上拉，不能保证接收器主动输出高电平时将其限制在 3.3V。R231 的串联作用也不能替代电平转换。TI 的接收输出典型曲线可超过 3.6V，不能用 VOH 最小值 2.7V 推断实际输出不高于 3.3V。

原 ARM 图纸是 GD32F303Cx，RS485 RX=PA10；官方管脚表将 PA10 标为 5VT。ESP32-C3 GPIO 输入高电平规格上限为 VDD+0.3V，即 3.3V 供电时约 3.6V。因此同一个收发器换 ARM/ESP，并不等价于输入电气条件相同。

**已确认的是设计没有保证 ESP RX 电平兼容；尚未确认实机 GPIO20 是否超限。** 若实际高电平超过允许范围，可能产生输入钳位电流或可靠性问题。单凭这一接收侧问题，仍不能推导 BMS 为什么四声；必须证明它如何影响控制器发送、供电或 BMS 状态。

资料：[TI SN65176B/SN75176B 数据手册，5.5、图5-4/5-5](https://www.ti.com/lit/ds/symlink/sn75176b.pdf)；[GD32F303xx，PA10/5VT](https://www.gd32mcu.com/data/documents/datasheet/GD32F303xx_Datasheet_Rev2.2.pdf)；[ESP32-C3，5.4 DC 特性](https://documentation.espressif.com/esp32-c3_datasheet_en.html)。

### 8.3 Q3 是逐位换向，并非整帧保持发送

TX 同时接 U31 DI 和 Q3 基极网络。Q3 为 MMBT5551；R233、R245 各1kΩ。Q3 集电极接 DE 与低有效 RE，R115=1kΩ 上拉至5V，发射极接地。

| TX 状态 | Q3 | DE/RE 节点 | U31 行为 |
| --- | --- | --- | --- |
| 低，发送0 | 截止 | 高 | 驱动使能，DI=0；接收禁用 |
| 高，发送1/停止位/空闲 | 导通 | 低 | 驱动高阻，接收使能；总线高电平靠偏置恢复 |

所以软件 DE=-1 不构成“漏配方向脚”。3.3V TX 高电平也满足 U31 DI 的 VIH≥2V 要求；Q3 实际翻转速度及是否饱和需看波形，不可仅凭两种 MCU 的驱动强弱归因。

图中 R120=5.1kΩ 上拉 A、R117=5.1kΩ 下拉 B，外侧 A/B 各串100Ω（R124/R116），未显示终端电阻。此电路发送1时依赖偏置，不应在未查明 BMS 偏置/终端的情况下随意加120Ω。

条件计算：仅考虑本板5V偏置、外侧一个120Ω跨接负载、忽略接收输入和其他偏置，外侧差分约 `5×120/(5100+100+120+100+5100)=57mV`；U31管脚侧约152mV。它们低于 SN65176B 需要保证接收高状态的 +200mV 门限。这里只说明此拓扑对负载敏感，不能声称 BMS 实际有120Ω或实际差分就是该数值。

TX 未配置且高阻时，基极电阻网络将 TX 向地拉，Q3 截止，可能使 U31 处于发送0状态。这一启动/重新连接窗口也需要记录；用户已说明问题随建立通信出现，不能假定它只发生在 ESP 上电。

### 8.4 有先后顺序的实测

1. 确认 U30/R228 装配及 CANH/CANL 是否连 BMS。若连着，先只拔 CAN 两线做对照，不改屏幕 NSS、不改查询帧。
2. 示波器测 GPIO20 相对 GND_COM 的高电平及尖峰；同时测 U31 RO，覆盖 BMS 回复期间。万用表只能初查空闲电压，不能证明整个收帧期间电平合规。
3. 测 GPIO21、DE/RE 节点及 A-B 差分，确认发送1/停止位的恢复幅度和时间；9600时每位约104µs。普通逻辑分析仪的数字判定无法代替过压和差分幅度测量。
4. 在 BMS MCU 接收端记录从接入前至四声结束的9600 8N1数据，与 ARM 对照首帧、额外字节、断续、间隔和 CRC。BMS 接收的正常查询应完整为 `7C 78 24 80 01 00 00`。

硬件分析阶段的优先级：若CAN也连接，先排除固定显性；无CAN连线时，优先核实RX电平兼容和逐位换向后的总线波形。第8节分析阶段未改生产代码；后续固件调整见第9节。未烧录。

## 9. 屏幕 NSS 改为硬件下拉后的固件调整

# DSP 联调栈溢出修复

日期：2026-10-14。联调版本：`0.6.8-dsp-dev`。

## 实机证据

`0.6.7-dsp-dev` 开机约3.3秒，首次打印DSP摘要时出现 `A stack overflow in task direct_dsp` 并重复重启。完整摘要同时显示 `tx=23 tx_err=0 rx_err=0 rx_bytes=0 frames=0`。这证明驱动接受查询但没有收到DSP字节；它不能证明GPIO线上确实到达DSP，也不能把没有回复归因于CRC或帧长。

设备的ELF指纹 `706caf366645b2e9458ce4780ef50d101645ce971c6498316aeacc48629ffa24` 与上版归档及保留ELF一致，使用这个ELF解析崩溃地址。`dsp_task` 编译固定帧为672B；日志捕获钩子固定帧272B；newlib `_vfprintf_r/_svfprintf_r` 固定帧各1152B，另有日志/VFS等调用开销。旧正常查询任务同步调用多参数报告，主机模拟无法复现实机RTOS栈空间。

最后硬件保护报告的 `0x3fca11f0..0x3fca17f0` 在精确map中是 `xIsrStack`，大小1536B，不是DSP任务分配的4096B。不能据此改变DSP任务栈大小或直接增加中断栈。

## 修复

- DSP UART owner正常轮询只做收发、协议解析、计数和快照更新，移除诊断格式化及同步回调。
- `arm_poll_tick()` 在已有6144B主循环任务中消费诊断和通知；主循环与UART owner之间复制快照并释放mutex，再打印或调用网络/BLE回调。
- 25真实回读确认和超时均记为待消费结果。消费结束前保持原 `s_write.pending`，拒绝新的参数写入和升级，避免旧结果被误用于新同地址命令。
- 完整且有效的控制快照合并为最新版本；未知配置仍然不能填零上报。
- DSP报告和USB `status` 拆为短行；十六进制前缀直接查表，不在循环里调用snprintf。调试日志捕获仍保留。
- 保持DSP任务4096B、主循环6144B、USB6144B及ISR1536B，未通过扩栈占用TLS预算，也未新增堆分配。固定通知存储很小，编译内存结果保存在验证报告。
- 新增 `stack_min_free`（DSP）和 `consumer_stack_min_free`（报告任务），ESP-IDF单位是字节，无需乘4。USB状态另有USB任务水位。

精确Device ELF对比：DSP任务固定栈帧从672B降到400B，固定DRAM增加104B；没有增加任务分配栈。新ELF指纹为 `ec529b1bea563428046c4abc880066974c126c44188f279f9431314acd2aa66e`。固定栈帧数字不等于整个调用链峰值，仍需实机水位。

## 验证

回归测试先在上版实际提取的DSP任务中禁止格式化，确实复现owner日志断言失败。修复后验证日志和回调只在消费上下文执行、mutex已释放、确认/超时只通知一次、通知期间保持忙、同地址新写被拒绝、快照保留最新版本；此前03/04/25及接收器测试保留。

独立源码副本从上一联调快照继承，只更新本次DSP/USB修复与相关测试，不覆盖共享工程的配网开发版本。全量回归、Device构建、固件标识与校验检查属于软件验证；没有烧录设备或证明栈溢出已在硬件消失。

## 升级后的验收

用Device `app.bin` 应用更新保留SN和WiFi；整片4MB镜像会覆盖身份及配网。

1. 确认启动版本为 `0.6.8-dsp-dev`，运行至少60秒，跨过首次报告和30秒报告点，没有panic/reboot。
2. 发送USB `status`（换行），记录DSP/主循环/USB的最低栈余量，及MQTT的before_connect/connected内存余量。
3. 若DSP仍 `rx_bytes=0`，在GPIO1→DSP RX、DSP TX→GPIO0两侧抓115200 8N1。期望查询03为 `01 05 03 00 00 00 00 4F 95`，04为 `01 05 04 00 00 00 00 FA 55`；检查DSP供电/运行、接收方向、电平和共地。已有配置确认日志使用USB，不占UART0。
4. 若开始收到字节，按crc/len/timeout及03/04计数继续定位。版本/完整00/01/02设置同步仍缺真实DSP协议及原ARM持久配置，不发送猜测值。

配网的云绑定公钥告警是继承快照中的独立功能状态，不是这次DSP栈溢出的依据。

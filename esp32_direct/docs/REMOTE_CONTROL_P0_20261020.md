# 远程控制 P0：实现、证据及验收边界

本轮按用户粘贴的完善方案继续实现。范围为普通 MQTT 命令幂等、过期和真实阶段，以及客户端能力过滤；没有实现未经确认的 DSP 开关机映射。

## 固件契约

| 情况 | 回执/行为 |
| --- | --- |
| 接收有效任务 | `stage=acknowledged`，不表示参数已生效 |
| ESP 保存并提交串口同步完成 | `stage=submitted`，`submitted_args` 为实际量化提交值，`desired_revision` 为期望配置版本 |
| 查询请求完成受理 | `stage=completed`，参数/遥测仍通过各自上报链路返回 |
| 相同 task_id、相同有效内容 | 重放当前或最终回执，不再执行 |
| 相同 task_id、不同有效内容 | `IDEMPOTENCY_CONFLICT`，保留原任务缓存和服务端执行状态 |
| expires_at 到期 | `EXPIRED`，不执行 |
| 带期限但 SNTP 未完成 | `CLOCK_UNSYNCED`，不执行 |
| 缓存已满 | `BUSY`，不提前驱逐仍有效的记录 |

缓存 8 项，终态保存 10 分钟，处理中不驱逐；仅在本次启动期间有效，不承诺跨重启唯一执行。旧无 task_id/无期限消息保持兼容，但不具备对应幂等/过期保证。终态序列化不依赖动态分配，避免低内存时已经执行但缓存永远停留在 ACK。

direct 没有 DSP 配置采纳回读证据，因此不发送 `applied`，也不以本地 desired store、串口发送成功或 config 上报冒充 DSP 确认。

## 云端与客户端

- 普通命令默认 5 分钟期限，经设备服务完整透传到 MQTT，离线补发保留原始期限。
- `submitted` 独立收口并显示“已保存并提交，设备生效未确认”；ACK/执行中不发送执行成功通知。
- 回执按 MQTT 路由的 SN 绑定，数据库使用原子状态推进，重复及延迟 ACK 不回退终态。
- 同任务冲突属于不同请求的诊断，不能把原任务改成失败。
- App 的 AC 开/关分别要求设备能力列表明确返回 `is_enabled=true`；接口失败、缺字段、禁用及类型异常均不可发送。
- 利用固件现有 INFO 的 `dsp_protocol=direct_uart_03_04_25` 识别 direct；能力接口和后端写入口共同禁止尚不支持的 AC 命令。协议标识无 TTL，缺失/未知 INFO 不清除已知限制。

能力识别边界：服务器首次收到该 INFO 前、Redis 全部丢失且设备尚未重新上报时，仍沿用型号能力以兼容旧 ARM，不能宣称此时已识别 direct。Redis 查询异常时 AC 写入拒绝。普通通知沿用原有 best-effort 投递，不承诺可靠补发。

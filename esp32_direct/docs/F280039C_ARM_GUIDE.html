F280039C 常驻 bootloader —— ARM(GD32) 侧指南

链路：云端 → ESP32 → ARM(GD32) → SCI-B → DSP(F280039C) |  DSP 侧：bootloader 于 0x080000~0x081FFF，App 从 0x082000

结论：协议没变，ARM 侧几乎不用改 ✓

这是刻意的设计选择 ✓：DSP 侧的 iap.c（协议层）是 从 F28335 bootloader 原样移植的 ✓，一个字符都没改 ✓。因此：

ARM 侧的东西是否要改原因
IAP 帧格式（HR / 擦除请求 / 数据包 / EOT）不变 ✓ DSP 侧代码同一份 ✓
擦除应答案（13 字节 01 10 04 38 … 11 03 D1）不变 ✓ DSP 逐字节回同样的常量 ✓
包地址编码 Addr = 0x01FE + 0xFF×包号不变 ✓ DSP 自己换算成 Flash 地址 ✓（ARM 只发包号 ✓）
CRC16-Modbus（命令帧低字节先 / 数据帧高字节先）不变 ✓ DSP 两种都接受 ✓
每包 1024 字节 / 最多 367 包容量变了 App 区 188144 字（367 KB）；F28335 是 196608 字（384 包）✓ 见下
下载的镜像内容必须换 F280039C 的 .bin（由 pack_f28003x.py 生成）✓

一、DSP 侧时序（与 F28335 完全一致）

DSP 上电/复位 ──► bootloader 启动
                  ├ App 无效（空白/CRC 不过）→ 一直监听，直到镜像写成功 ✓
                  └ App 有效 → 开 3 秒窗口等主机 ──┬ 收到 "HR" → 进入升级 ✓
                                                  └ 超时 → 校验镜像头后跳进 App ✓

升级过程（ARM 视角）：
  ARM  →  复位 DSP（或让 App 主动交接：写 0xBFFE 的握手字后跳到 0x080000）
  DSP  →  "HR"               （就绪，可重复询问）
  ARM  →  01 10 04 38 00 02 04 00 00 00 00 C3 DD      （擦除请求）
  DSP  →  01 10 04 38 00 02 04 00 00 00 11 03 D1      （擦除开始应答）
  DSP  →  （擦除 App 区：扇区 2~47，F28003x 是硬件 Bank Erase，很快 ✓）
  DSP  →  "CR"               （擦除完成）
  ARM  →  02 AddrH AddrL <1024 字节> CRCH CRCL        （数据包，Addr=包号编码）
  DSP  →  "CR"               （每包一条）
  ...重复到发完...
  ARM  →  02 00 FF 45 4F 54  （EOT）
  DSP  →  校验写回 → 跳进新 App（不再复位，直接跑 ✓）

二、真正需要 ARM 做的事

  1. 下发 F280039C 的镜像 ✓ —— 由云端用 py host\pack_f28003x.py app.out app.bin --version … 生成 ✓ （每字高字节先，与 DSP 侧 iap_words[i]=(hi<<8)|lo 一致 ✓）。
  2. 容量上限改成 367 包 ✓ —— 原来的 384 包上限是按 F28335 的 196608 字算的 ✓； F280039C 的 App 区是 188144 字（0x082000~0x0AFEEF，367 KB）→ 上限 367 包 ✓ （DSP 侧 IAP_MAX_PACKET_INDEX = 0x2DEF0/512 - 1 = 366，即包号 0~366 ✓）。 超了 DSP 会拒收（idx > IAP_MAX_PACKET_INDEX ✓）。
  3. 单槽，不再需要“选 bank” ✓ —— 旧 LDFU 三 bank 方案才有"写哪一份镜像"的问题 ✗； 现在只有一份 App 区 ✓，云端下发同一份即可 ✓。
  4. 可选：校验 DSP 回报的版本号（镜像头字 8..9 的 version ✓）。

三、时间参数（F280039C 更快，旧超时仍然安全）

环节F28335 实测/设定F280039C建议
擦除（整个 App 区）约 9.4 s（8 扇区逐扇区） 硬件 Bank Erase，明显更快 ✓ 沿用 12 s 超时 ✓ 安全
每包应答1.2 s 超时Flash 编程更快 ✓ 沿用即可 ✓
HR 等待2 s × 5 次bootloader 窗口是 3 s ✓ 首次询问留 ≤3 s 内 ✓，重试要重新复位/交接 ✓

注意 DSP 侧有两个独立超时：IAP_FRAME_TIMEOUT_MS = 5000（等一帧的开始 ✓） 与 IAP_BYTE_GAP_MS = 20（帧内两字节之间 ✓）。 所以一个帧内的字节必须连续发 ✗ —— 中间插入几百毫秒的其他事务会触发断帧 ✓。

四、触发升级的两条路（都不改协议）

方式做法适用
复位 + HR ARM 拉 DSP 复位（或让 DSP 软复位）→ 3 秒窗口内发 "HR" ✓ 最常用 ✓ 与 F28335 时代一致 ✓
App 主动交接 ARM 发业务命令 → App 自己写 0xBFFE 握手字并跳到 0x080000 ✓
然后 ARM 立即发 "HR" ✓（bootloader 跳过窗口直接监听 ✓）		 不想复位、要平滑进入升级时 ✓

⚠️ 若 DSP 处于「App 有效且已过窗口」的运行态，那时它不在监听 ✗ —— 直接发 HR 不会有任何回应 ✓。必须先复位/交接 ✓。

五、失败处理（不变，但结果更好）

失败点现象结果
发 HR 无回应超时DSP 仍在跑旧 App ✓（不影响生产）
擦除无应答超时旧 App 已被擦 ✗ → DSP 停在 bootloader 监听 ✓ 可重试 ✓
传一半断电—镜像头 CRC 不过 → bootloader 不跳转 ✓ 继续监听 ✓ 重传即可 ✓
数据传输 CRC 错DSP 回 NAK/不应答重发该包（现有重试逻辑 ✓）

关键改进：升级"写了一半"的镜像永远不会被执行 ✓（bootloader 的 magic+长度+CRC32 三重校验 ✓）→ 所以 ARM 侧不需要复杂的回滚逻辑 ✓，上报失败让用户重试即可 ✓。

六、ARM 侧改动清单（照这个改就够）

  1. 把镜像换成 F280039C 的 .bin ✓（pack_f28003x.py 产出 ✓）
  2. 包数上限 384 → 367 ✓
  3. 删除/绕过一切"bank 选择"逻辑（若有）✓
  4. HR 首次等待 ≤3 s（bootloader 窗口）✓
  5. 其余协议代码保持原样 ✓✓

七、联调验收

  1. 发 HR 能收到 "HR" ✓
  2. 擦除请求能收到 13 字节应答，随后收到 "CR" ✓
  3. 9 包（≈8 KB）传输完成后，DSP 串口出现新版 App 的启动横幅 ✓
  4. 再升级一次（换版本号）→ 横幅版本随之变化 ✓
  5. 传输中途断电 → 重新上电仍是旧版本 ✓

# WiFi 回归对照与恢复修复

日期：2026-10-14。版本：`0.6.9-wifi-dev`。

用户反馈v0.6.6已在同机连接MQTT，更新DSP联调固件后WiFi连续失败。这是需要按版本回归排查的证据，不能先归因于路由器或密码。

## 对照证据及限制

- 真正v0.6.6 Device app嵌入ELF指纹：`a5caf13ae7e1b48dc52a07d0d2fdd110a64a10025c309c723cf2db5cbb81fc55`，由归档app描述符读出。
- 一个名为 `tmp/dsp_before_v066/production.elf` 的备份实际是 `0.6.4-onboarding-dev`，不能用作v0.6.6基线。另一个聊天也在共享构建目录工作，因此必须按指纹确认。
- 使用真正v0.6.6 app.bin反汇编与v0.6.8比较：wifi_event_handler、wifi_sta_init、wifi_sta_connect、setup_wifi及配网回调的指令数量、寄存器和控制流结构一致，链接地址不同。它不能证明整体调度、无线运行时状态或硬件行为完全相同。
- 真正v0.6.6归档记录静态DRAM为25836+51416B，v0.6.8为25836+51992B，增加576B。更早的配置快照与v0.6.8的WiFi、BT、COEX、FreeRTOS、LWIP、PM、NVS配置无变化；这份快照不是完整精确v0.6.6配置，因此报告明确标识来源。
- v0.6.8新增了配网开发快照和DSP轮询/诊断，不能仅凭没有改wifi_sta函数就排除间接回归。
- 日志reason2/205/203说明连接阶段反复失败；v0.6.6成功那次也出现过2/205。现有日志没有实际SSID及稳定的关联/IP状态，不能单凭原因码断定密码错误。

## 本次确定修复

旧代码达到五次失败后执行esp_wifi_stop/start并返回，STA_START事件只打印日志，没有调用esp_wifi_connect。驱动start不会替应用自动连接，于是要等主循环下一轮约30秒超时才能重新请求。

本次保存连接意图：初始STA_START在没有配置请求时不连接；有效配置请求发生在驱动启动前则由STA_START启动连接；重启后继续连接当前配置。显式force_disconnect会停止事件自动重试，新的配置请求可恢复。

WiFi读取NVS失败不再将空缓冲当作有效配置；release显示凭据来源、SSID、密码长度、开始连接、关联后等待DHCP以及Got IP，绝不打印密码。未更改SSID/密码、射频配置、WiFi缓冲数、DSP栈修复和TLS动态缓冲。

这个缺口解释失败后的恢复停顿，不能当作第一轮认证失败的既证根因。本次还没有实机恢复证明。

## 实机对照

1. 保持同一设备、同一位置、同一路由器及NVS配置，不先重新配网或恢复出厂。
2. 用归档 `release/esp32c3_v0.6.6_20261013/device/app.bin` 做应用更新，观察至少60秒。记录版本及是否出现MQTT connected。若仍失败，需要继续核对保存配置或环境变化；不能把修改时间相关性直接当确定根因。
3. 应用更新为本次 `0.6.9-wifi-dev`，记录 `WiFi from NVS`（SSID及pass_len）、`connecting to SSID`、`STA associated; waiting for DHCP IP`、`Got IP`、断开原因和TLS日志。
4. 若v0.6.6在相同配置下成功而本版失败，则版本回归被实机对照确认，按这些阶段继续定位。若重启WiFi后本版立即继续请求，只证明重连缺口修复，不等于认证问题已解决。

应用更新保留普通NVS和factory身份；整片4MB镜像会覆盖WiFi及SN/PIN。包内整片镜像仅供明确的首次烧录，不用于这次保留配置的回归对照。

## 软件验证

新增测试提取实际WiFi函数，在旧版本复现第五次失败后STA_START没有触发连接的断言失败。覆盖启动前/后凭据请求、重启后使用原配置、显式停止重连、新配置恢复、配置失败、获取IP重置计数。它不模拟RF认证，也不替代设备验收。
